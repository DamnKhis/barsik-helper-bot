## 3. База данных (`app/db.py`)

Доработай (или адаптируй существующие в `app/db.py`) модели для двух основных таблиц так, чтобы они не конфликтовали с `bars-dashboard.html`:

### Таблица 1: `users` (Пользователи и их права)
* `id` — Primary Key.
* `telegram_id` — `BigInteger`, уникальный, индексируемый (ID юзера в Telegram).
* `username` — `String`, nullable (никнейм в ТГ).
* `full_name` — `String`, nullable.
* `role` — `String`: `'user'` (по умолчанию), `'manager'`, `'admin'`.
* `is_pending_manager` — `Boolean` (по умолчанию `False`). Флаг того, что юзер подал заявку на получение прав менеджера и ждет одобрения админа.
* `created_at` — `DateTime`.

### Таблица 2: `dialog_history` (История диалогов и тикеты)
* `id` — Primary Key.
* `user_id` — `BigInteger` (ForeignKey на `users.telegram_id`).
* `question` — `Text` (вопрос пользователя).
* `answer` — `Text`, nullable (ответ ИИ или ответ менеджера).
* `answered_by` — `String`: `'ai'`, `'manager'` или `'none'` (если ответа еще нет).
* `ticket_status` — `String`:
  * `'none'` — ИИ знал ответ и ответил сам;
  * `'open'` — ИИ ответил, что не знает ответ (тикет создан и ждет менеджера);
  * `'in_progress'` — тикет принят менеджером в работу;
  * `'closed'` — менеджер ответил на тикет, вопрос закрыт.
* `manager_id` — `BigInteger`, nullable (ID менеджера, который принял тикет).
* `created_at` — `DateTime`.

## 4. Хранение контекста ИИ в Redis

Контекст диалога для ИИшки должен храниться в **Redis**.

* **Ключ:** `str(user_id)` (где `user_id` — это `telegram_id` пользователя).
* **Значение:** JSON-список сообщений в хронологическом порядке: приход от юзера -> ответ -> вопрос -> ответ и т.д.
* **Пример JSON-структуры по ключу `user_id`:**
  `[{"role": "user", "content": "Вопрос 1"}, {"role": "assistant", "content": "Ответ 1"}, {"role": "user", "content": "Вопрос 2"}, {"role": "assistant", "content": "Ответ 2"}]`
* Реализуй сервис `RedisContextService` с методами:
  * `get_context(user_id: int) -> list[dict]` — получение текущего контекста юзера.
  * `append_pair(user_id: int, question: str, answer: str)` — добавление вопроса юзера и полученного ответа в конец списка в Redis.
  * `clear_context(user_id: int)` — очистка контекста (при необходимости).

## 5. Строгое разделение ролей и сценарии работы

**ГЛАВНОЕ ПРАВИЛО:** Когда пользователь является **Админом** или **Менеджером**, он **НЕ общается с ИИ** и не выступает в роли обычного юзера. У каждой роли строго свое меню и свои функции («чисто свои приколы»).

Проверка роли выполняется при `/start` и через фильтр/мидлварь по таблице `users`. Также добавь чтение `ADMIN_IDS` из `.env` — если `user_id` есть в этом списке, при старте ему сразу назначается роль `'admin'` в БД.

### Роль 1: Обычный пользователь (`role == 'user'`)
1. **Команда `/start`:**
   * Юзер сохраняется в таблицу `users` с ролью `'user'` (если еще не создан).
   * Бот присылает приветствие и кнопку **«Задать вопрос»** (плюс дополнительную кнопку **«Запросить права менеджера»**, которая выставляет `is_pending_manager = True` для одобрения админом).
2. **Начало диалога:**
   * После нажатия кнопки **«Задать вопрос»** бот переводит юзера в состояние диалога (`UserStates.in_dialog`) и ждет сообщения.
   * Юзер пишет вопрос -> бот берет из Redis историю по ключу `user_id` и вызывает функцию ИИ (пока заглушку), передавая туда вопрос и контекст из Redis.
3. **Обработка ответа ИИ:**
   * **Если ИИ знает ответ:**
     * Бот отправляет ответ юзеру.
     * Сохраняет связку `вопрос + ответ` в Redis по ключу `user_id`.
     * Сохраняет запись в таблицу `dialog_history` (`answered_by='ai'`, `ticket_status='none'`).
   * **Если ИИ ответило, что НЕ знает ответ на вопрос:**
     * Бот пишет юзеру, что не знает ответа и переводит вопрос на менеджера.
     * Сохраняет вопрос и системный ответ в Redis по ключу `user_id`.
     * Сохраняет запись в `dialog_history` со статусом тикета `ticket_status='open'` и `answered_by='none'`.
     * Рассылает уведомление свободным менеджерам (`role == 'manager'`) о новом тикете с инлайн-кнопкой **«Принять тикет»**.

### Роль 2: Менеджер (`role == 'manager'`)
Менеджер — это бывший обычный юзер, которому админ одобрил права. С ИИ не общается, с юзером в свободном чате не переписывается — работает строго через систему тикетов.
1. **Команда `/start`:**
   * Показывает меню менеджера: кнопка **«Неразобранные тикеты»** (список записей из `dialog_history`, где `ticket_status == 'open'`).
2. **Прием и ответ на тикет:**
   * Менеджер видит вопрос юзера, на который ИИ не смогла ответить, и нажимает инлайн-кнопку **«Принять тикет»** (`callback_data="take_ticket:{ticket_id}"`).
   * В таблице `dialog_history` статус меняется на `'in_progress'`, записывается `manager_id`.
   * Бот просит менеджера ввести текст ответа на этот вопрос (состояние `ManagerStates.waiting_for_answer`).
   * Менеджер отправляет текст -> бот пересылает этот ответ пользователю, задавшему вопрос (`bot.send_message(user_id, ...)`), обновляет запись в `dialog_history` (`answer=...`, `answered_by='manager'`, `ticket_status='closed'`) и дописывает ответ в Redis-контекст этого юзера.

### Роль 3: Админ (`role == 'admin'`)
Админ определяется по `user_id`. С ИИ не общается, тикеты юзеров не решает. У него своя админ-панель.
1. **Команда `/start`:**
   * Если `user_id` имеет роль `'admin'`, открывается админка с двумя кнопками:
     * **«Добавить доку»**
     * **«Одобрить менеджера»**
2. **Функция «Добавить доку»:**
   * При нажатии бот переходит в состояние `AdminStates.waiting_for_doc` и просит прислать файл.
   * Админ отправляет документ (`message.document`).
   * Бот скачивает файл и **локально сохраняет его в папку проекта** (например, `./uploaded_docs/{filename}`). Никакую обработку/парсинг запускать не надо — только локальное сохранение и ответ админу, что файл сохранен.
3. **Функция «Одобрить менеджера»:**
   * При нажатии бот выводит список юзеров, подавших заявку (`is_pending_manager == True`), либо позволяет выбрать/ввести `user_id` пользователя из таблицы `users`.
   * Под каждым кандидатом инлайн-кнопка **«Одобрить»** (`callback_data="approve_manager:{target_user_id}"`).
   * При нажатии у пользователя в БД обновляется `role = 'manager'` и `is_pending_manager = False`, а самому пользователю уходит уведомление, что теперь он менеджер.

## 6. Заглушка для ИИ (`app/bot/services/ai_stub.py`)

Так как часть с ИИ трогать нельзя, создай изолированную функцию-заглушку, которую потом заменят на вызов реального RAG:
* На вход принимает: `user_id: int`, `question: str`, `context: list[dict]`.
* На выход отдает: `tuple[bool, str]` — `(known_answer, response_text)`.
* Для удобного тестирования сделай так: если в тексте вопроса есть фраза `"не знаю"` или `"сложный вопрос"`, функция возвращает `(False, "Я не знаю ответ на этот вопрос")`, что триггерит создание тикета для менеджера. На любые другие вопросы возвращает `(True, "Ответ ИИ с учетом контекста")`.
