# Обновление базы знаний: как документ попадает в ответы

Коротко про путь «документ → ответ» и про то, как проверить, что он действительно
прошёл. Появилось после разбора ситуации «PDF добавляли — отвечал, DOCX добавляли —
молчал».

## Путь документа

```text
Админ → «Добавить доку» → uploaded_docs/<файл>
      → kb_autosync.stage_document() → bars-kb/docs/source/<файл>
      → watcher (bars-kb watch) видит новый digest → пересобирает пакет
      → bars-kb/dist/<build_id> + dist/LATEST
      → бот читает LATEST на каждом поиске (kb_client) → отвечает
```

Важно: пересборка идёт по **всей** папке `docs/source`, поэтому если она прошла
успешно, в сборке оказываются все лежащие там документы. Если в базе нет нового
документа — значит пересборка не прошла (или не запускалась), а не «документ
не разобрался».

## Почему это раньше не было видно

Админ получал «Пересборка запустится автоматически в течение 60 с» и всё.
Пересборка могла не запуститься или упасть по причинам, которые в чате не видны:

| Причина | Что происходит | Как проявляется |
|---|---|---|
| нет `QWEN_API_KEY` | `bars_kb.cli` отказывается публиковать mock/hash-сборку и выходит с кодом 2; watcher умирает | в логе приложения `KB autosync остановился с кодом 2` |
| не поднят Qdrant | сборка падает после обогащения, `dist/` не меняется | `watch: rebuild failed, will retry: ... Connection refused` |
| приложение запущено из каталога без `.env` | тот же отказ mock/hash | «KB autosync не запустился» |
| `KB_AUTOSYNC=0` | watcher не стартует | в ответе админу сказано «запустите bars-kb sync вручную» |
| документы лежат не в той папке, которую смотрит watcher | digest не меняется | пересборки нет вообще |

Во всех случаях бот продолжает отвечать из **предыдущей** сборки. Вопросы, чьи
темы пересекаются со старыми документами, получают ответ, а новые темы
(например, «Пропуск», которого в старых PDF нет вообще) — нет.

## Что теперь делает бот

`app/bot/services/kb_status.py` показывает правду о пакете:

* `snapshot()` — какая сборка в `dist/LATEST`, сколько документов и чанков, какой
  digest исходников в неё зашит (digest считается той же формулой, что в
  `bars_kb.pipeline.source_fingerprint`);
* `status.stale` — папка с документами новее сборки, то есть часть документов
  ещё не пересобрана;
* `status.has_document("БП Пропуск.docx")` — есть ли конкретный файл в сборке.

Поэтому после загрузки документа админ видит:

```text
Документ добавлен в базу знаний: БП Пропуск.docx
Текущая сборка — сборка 20261114T205237_a5023733: документов 3, чанков 102.
Этого документа в сборке пока нет.
Пересборка запустится автоматически в течение 60 с — сообщу, когда документ окажется в базе.
```

а затем одно из двух (таймаут — `KB_CONFIRM_TIMEOUT_SEC`, по умолчанию 900 с):

```text
✅ Документ в базе знаний: БП Пропуск.docx
сборка 20261115T224248_1e01c5cb: документов 5, чанков 132.
Регламент можно спрашивать прямо сейчас.
```

```text
⚠️ Документ «БП Пропуск.docx» пока не попал в базу знаний.
Похоже, пересборка не прошла: папка с документами новее сборки 20261114T205237_a5023733.
Проверьте лог приложения (KB autosync) и что Qdrant поднят, либо запустите bars-kb sync вручную.
```

То есть «документ добавлен» больше не означает «документ в базе».

## Второй источник: решённые обращения поддержки

Рядом с документацией лежит папка с решёнными обращениями. Туда попадают только те
тикеты, которые техподдержка отметила как полезные — этим занимается бот, пайплайн
их просто забирает в сборку.

```text
bars-kb/docs/
├── source/                     # документация (doc_kind=doc)
└── support_answers/            # решённые обращения (doc_kind=support)
    ├── KAN-23.md               # диалог + «## Вопрос N / ## Ответ поддержки N»
    └── attachments/KAN-23/*.jpg  # картинки из диалога
```

Что делает пайплайн:

* файлы `.md` из `support_answers/` разбираются как обычные документы, но с
  `kind="support"` — в payload у чанков появляется `doc_kind=support`, а в цитате
  видно заголовок обращения («Источник: KAN-23: полезный ответ поддержки, Ответ
  поддержки 1»);
* картинки из `attachments/<KEY>/` разрешаются относительно `.md`, копируются в
  `data/images` и попадают в сборку как обычные чанки-скриншоты (их описывает
  vision-модель, как и картинки из PDF/DOCX);
* «История диалога с ИИ» и реплики пользователя без ответа в поиск не попадают:
  там шум («оаоаво») и персональные данные (имя, @username, Telegram ID);
* тикет, в котором поддержка не ответила, пропускается — в логе видно
  `no chunks for KAN-21.md (support) — документ пропущен`.

Состав сборки отражается в манифесте:

```json
"counts": {"documents": 6, "chunks": 134, "support_documents": 1, ...},
"sources": [{"kind": "doc", "files": [...]}, {"kind": "support", "files": [...]}]
```

### Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `SUPPORT_DOCS_PATH` | `docs/support_answers` | папка с решёнными обращениями |
| `SUPPORT_INDEX_MODE` | `dialogs` | что индексировать (см. ниже) |
| `KB_AUTOSYNC_SUPPORT` | `SUPPORT_ANSWERS_DIR` | папка, за которой следит watcher приложения |

Режимы `SUPPORT_INDEX_MODE`:

| Режим | Что попадёт в поиск |
|---|---|
| `dialogs` (по умолчанию) | пары «Вопрос N / Ответ поддержки N», а если пар нет — блок «Диалог» при наличии ответов поддержки |
| `qa` | строго пары «Вопрос N / Ответ поддержки N» |
| `answers` | только блоки «Ответ поддержки N» |
| `all` | весь файл как есть (для отладки) |

Как именно пара превращается в чанк и как по нему потом ищется — в разделе
«Как по обращениям ищут» ниже.

### Пересборка

Пересборка запускается изменениями **в обеих папках**: watcher приложения получает
`--source docs/source --support-source docs/support_answers`, а digest считается
по объединённому набору файлов (`source.digest` в манифесте). Ветка CI смотрит и на
`bars-kb/docs/support_answers/**`.

```bash
# вручную: оба источника (по умолчанию, если папки не заданы)
PYTHONPATH=bars-kb/src .venv/bin/python -m bars_kb.cli sync

# только документация
PYTHONPATH=bars-kb/src .venv/bin/python -m bars_kb.cli sync --source docs/source --no-support

# только конкретные обращения
PYTHONPATH=bars-kb/src .venv/bin/python -m bars_kb.cli sync \
    --source docs/source --support-source docs/support_answers
```

Важно: если папка-источник задана явно (`--source`), обращения к ней **не**
добавляются автоматически — передавайте `--support-source` (так же делает CI).


### Как по обращениям ищут: пара «вопрос+ответ» одним чанком

Документация и обращения ищутся по-разному, поэтому у них разная нарезка:

| | документация | решённое обращение |
|---|---|---|
| чанк | раздел в 800–1500 символов | одна пара «вопрос + ответ», `chunk_type=support` |
| `raw_text` | текст раздела | `Вопрос: …\n\nОтвет: …` (это видит генератор ответа) |
| `enriched_text` (по нему dense + BM25) | breadcrumb + summary + вопросы раздела + текст | breadcrumb + «Вопрос пользователя: …» + «Похожие формулировки: …» + «Кратко: …» + фрагмент ответа |
| `parent_text` | контекст раздела | вся пара целиком |
| раздел | `1.1 Главное меню` | `Вопрос 1` |

Почему так: в обращении искать нужно **по формулировке вопроса** — пользователь
спросит так же, как спрашивал автор тикета, — а отвечать нужно **ответом
поддержки**. Поэтому вопрос и ответ лежат в одном чанке, а в индекс идут
перефразировки вопроса, которые генерирует отдельный промпт
(`bars_kb/enrich/support.py`): 3–5 вариантов формулировки, краткая суть решения
и термины. Промпт обогащения документации для тикета не подходит — на коротком
тексте он выдаёт описание самой переписки («пользователь задал вопрос с
опечаткой…»), и в вектор уходит шум вместо вопроса.

Проверка на паре «Не могу оформить пропуск: заявка висит в статусе "Проверка
пройдена"» (реальные модели, поиск через бота):

| запрос | результат |
|---|---|
| точный вопрос обращения | `ANSWER` 0.98 → `KAN-100, Вопрос 1` |
| «не получается получить пропуск, что делать» | `ANSWER` 0.89 → `KAN-100, Вопрос 1` |
| «кто должен согласовать заявку на пропуск» | `ANSWER` 0.98 → `KAN-100, Вопрос 2` |
| «пропуск не выдаётся, заявка где-то застряла» | `CLARIFY` 0.55, но тикет найден |

Последняя строка — про пороги уверенности ретривера: они калибровались на
документации, и короткий тикет иногда не дотягивает до `ANSWER`, хотя попадание
верное. Это отдельный шаг (пересчёт порогов и, при желании, второй проход поиска
с фильтром `doc_kind=support`).

### Контроль качества: eval по обращениям

Сборка сама генерирует `support_golden.jsonl` — по контрольному вопросу на каждую
пару `support` (вопрос берётся из чанка), кладёт его в пакет и в `data/`.
`run_eval` прогоняет оба набора (документация + обращения) и в отчёте есть
разбивка:

```json
"by_type": {"text": {"questions": 7, "hit@1": 0.86}, "support": {"questions": 2, "hit@1": 1.0}}
```

Это сторож целостности, а не замер формулировок: он ловит «тикет пропал из
сборки», «сломался раздел», «сменился тип чанка». В CI `--eval` уже включён.

```bash
PYTHONPATH=bars-kb/src .venv/bin/python -m bars_kb.cli eval --top-k 8
```

## Проверка без запуска бота

```bash
# 1. что вообще есть в пакете (список сборок, звёздочка — актуальная)
PYTHONPATH=bars-kb/src .venv/bin/python -m bars_kb.cli builds

# 2. манифест актуальной сборки: документы и чанки
PYTHONPATH=bars-kb/src .venv/bin/python -m bars_kb.cli status

# 3. статус так, как его видит бот (stale + наличие файла)
PYTHONPATH=.:bars-kb/src .venv/bin/python -c "
from app.bot.services import kb_status
s = kb_status.snapshot()
print(s and s.short(), '| stale:', s and s.stale)
print('документы:', s and s.document_list())
"

# 4. пересобрать вручную, если watcher спит
PYTHONPATH=bars-kb/src .venv/bin/python -m bars_kb.cli sync --source bars-kb/docs/source
```

## Про DOCX отдельно

Формат разбирается штатно: у «БП Пропуск.docx» получается 18 чанков (13 текстовых,
4 таблицы, 1 схема бизнес-процесса, 1 изображение). Поиск по ним работает — проверено
на реальных эмбеддингах:

| Вопрос | Источник в ответе |
|---|---|
| «Как оформить пропуск и кто согласовывает заявку?» | `БП Пропуск > 5 Инструкция > 5.4 Оформление и выдача пропуска` |
| «Сколько времени занимает проверка службой безопасности?» | `БП Пропуск > 5.3 Проверка Службой безопасности` |

Слова «пропуск» нет ни в одном другом документе (в трёх старых PDF — 0 вхождений,
в «Справочнике БАРС-Офис» — тоже 0), так что при вопросе про пропуск поиск
обязан попадать в чанки docx — если он вообще в сборке.

Отдельная просьба к будущим правкам: у «Справочника БАРС-Офис» распознаётся всего
одна секция (заголовки не детектятся), поэтому в цитатах у него нет пути раздела.
